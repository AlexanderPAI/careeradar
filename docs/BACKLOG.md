# КарьеРадар — общий backlog

Документ объединяет план развития по версиям и подробную декомпозицию ближайших продуктовых направлений.

## Идентификаторы направлений

| Идентификатор | Значение | Назначение |
|---|---|---|
| `CORE` | Ядро продукта | Профиль, предпочтения, версии данных, качество и хранение данных |
| `MATCH` | Сопоставление | Объяснимая оценка соответствия профиля конкретной вакансии |
| `FEED` | Персональная лента | Избранное, статусы, скрытие и объединение вакансий |
| `MARKET` | Карта рынка | Зарплаты, спрос, компании, навыки и динамика рынка |
| `SKILL` | Навыки | Выявление пробелов, оценка их влияния и план развития |
| `INFRA` | Инфраструктура | Безопасность, reverse proxy, сервер и домен для production-развёртывания |

## Статус относительно версии 0.4.1

Статус определён по фактической реализации backend, frontend, моделей БД, миграций, агентов и промптов на 27 июля 2026 года.

Обозначения:

- **Частично** — в проекте есть используемая техническая или пользовательская основа, но критерии готовности задачи не выполнены полностью;
- **Не начато** — целевой пользовательский сценарий и необходимые данные отсутствуют;
- **Завершено** — все критерии готовности задачи реализованы.

Завершённых задач из backlog пока нет: существующие возможности `0.4.1` являются основой для части задач, но не покрывают их критерии готовности целиком.

Дополнительные факты аудита:

- подробный анализ вакансии и базовые рекомендации по резюме уже работают и не должны разрабатываться повторно;
- поддержка старого бинарного `.doc` заявлена в загрузчике, но фактически используется DOCX-ридер, поэтому надёжная поддержка `.doc` не подтверждена;
- в репозитории нет автоматических тестов;
- `frontend/db` содержит неиспользуемый прямой доступ к PostgreSQL, тогда как действующий интерфейс работает через защищённый backend API;
- в цепочке миграций остаётся служебная таблица `test`, не относящаяся к продуктовой модели.

## План релизов

### Правила версионирования

Версии проекта имеют формат `X.Y.Z`:

- `Z` — исправление ошибок без добавления новой функциональности, например `0.5.1`;
- `Y` — минорное обновление с новой функциональностью, например переход с `0.5.0` на `0.6.0`;
- `X` — мажорное обновление, обозначающее крупный этап зрелости продукта.

Все продуктовые этапы до завершения текущего roadmap увеличивают `Y`. Версия `1.0.0` является последней версией этого плана и обозначает завершение формирования КарьеРадара как системы постоянного карьерного мониторинга.

Bugfix-релизы заранее не планируются как отдельные продуктовые этапы. При необходимости они выпускаются между минорными версиями с увеличением `Z`: `0.5.1`, `0.5.2` и далее.

### Допущения календарного плана

- начало работ — 27 июля 2026 года;
- задачи выполняются последовательно и не перекрываются;
- небольшие связанные изменения оцениваются в рабочих днях;
- в конце каждого релиза предусмотрена короткая интеграционная и регрессионная проверка;
- план пересматривается после каждого релиза;
- незапланированный bugfix-релиз может сдвинуть последующие даты.

# Подробная декомпозиция

## CORE — фундамент продукта

`CORE` происходит от английского *core* — «ядро». Это задачи, которые создают общую основу для подбора вакансий, карты рынка, анализа навыков, карьерных маршрутов и работы с резюме.

### CORE-01. Зафиксировать модель карьерного профиля

Задачи:

- определить обязательные и необязательные поля профиля;
- разделить факты из резюме, выводы LLM и пользовательские предпочтения;
- хранить источник каждого навыка или утверждения;
- версионировать формат профиля;
- определить поведение при неполном резюме;
- зафиксировать реально поддерживаемые форматы резюме и либо добавить корректное чтение `.doc`, либо убрать его из разрешённых загрузок.

Критерий готовности:

- профиль имеет зафиксированную схему;
- подтверждённые факты невозможно спутать с предположениями LLM;
- для значимых данных можно определить источник.

### CORE-02. Добавить редактирование профиля

Задачи:

- добавить редактирование позиций, навыков, уровня, локации и формата работы;
- разрешить добавлять и удалять навыки;
- дать возможность подтверждать или отклонять предположения LLM;
- сохранять новую версию профиля;
- предлагать повторный поиск после изменения профиля.

Критерий готовности:

- пользователь может исправить профиль без повторной загрузки резюме;
- изменение профиля не переписывает незаметно результаты прошлых поисков.

### CORE-03. Добавить карьерные и поисковые предпочтения

Задачи:

- желаемые должности;
- зарплатные ожидания;
- города;
- удалённый, гибридный или офисный формат;
- тип занятости;
- нежелательные компании;
- нежелательные технологии и условия;
- обязательные и необязательные требования пользователя.

Критерий готовности:

- предпочтения учитываются при поиске и оценке вакансий;
- пользователь видит, какое предпочтение повлияло на результат.

### CORE-04. Добавить историю версий профиля

Задачи:

- хранить версии профиля и дату изменения;
- связывать каждый поиск с конкретной версией;
- показывать, по какой версии построена выдача;
- не пересчитывать прошлые результаты незаметно для пользователя.

Критерий готовности:

- каждый сохранённый поиск однозначно связан с состоянием профиля на момент запуска.

### CORE-05. Обеспечить наблюдаемость ключевого сценария

Задачи:

- добавить структурированные журналы поиска, парсинга и LLM-вызовов;
- измерять продолжительность и ошибки каждого этапа;
- учитывать количество найденных, отброшенных и недоступных вакансий;
- различать ошибки источника, LLM-провайдера и приложения;
- выдавать диагностический идентификатор операции.

Критерий готовности:

- по неуспешной операции можно установить этап и причину сбоя без доступа к персональным данным пользователя.

### CORE-06. Организовать контроль качества AI-функций

Задачи:

- подготовить обезличенные тестовые профили и вакансии;
- определить ожидаемые совпадения и несоответствия;
- проверять отсутствие выдуманного опыта;
- сравнивать качество провайдеров и версий промптов;
- запускать регрессионную проверку перед релизом;
- создать базовый набор автоматических тестов для нормализации профиля, прав доступа, репозиториев, API-контрактов и расчёта matching.

Критерий готовности:

- изменение модели, провайдера или промпта можно проверить на едином эталонном наборе.

### CORE-07. Определить политику хранения данных

Задачи:

- определить срок хранения исходных резюме;
- реализовать удаление профиля и связанных данных;
- определить правила архивирования;
- удалять загруженный файл по запросу пользователя;
- предусмотреть экспорт пользовательских данных;
- определить правила хранения снимков вакансий и AI-анализов;
- удалить или официально задействовать неиспользуемый прямой доступ frontend к PostgreSQL;
- исключить служебную таблицу `test` из продуктовой схемы с безопасной миграцией.

Критерий готовности:

- для каждого типа пользовательских данных определены срок хранения, способ удаления и связанные зависимости.

## MATCH — сопоставление профиля и вакансии

`MATCH` происходит от английского *matching* — «сопоставление». Направление отвечает за оценку конкретной вакансии: насколько она подходит пользователю, почему она подходит и какие существуют пробелы или риски.

### MATCH-01. Формализовать модель оценки

Задачи:

- определить влияние соответствия роли;
- учитывать уровень опыта;
- разделять обязательные и желательные навыки;
- учитывать доменный опыт;
- учитывать язык;
- учитывать локацию и формат работы;
- учитывать зарплату;
- определить стоп-факторы;
- определить правила работы с неизвестными данными;
- определить правила расчёта уверенности.

Критерий готовности:

- для каждого фактора описано его влияние на оценку;
- отсутствующие данные не считаются автоматически несоответствием;
- процент всегда сопровождается объяснением и уровнем уверенности.

### MATCH-02. Обновить контракт AI-анализа

Для каждой вакансии результат должен содержать:

- итоговый балл;
- категорию;
- подтверждённые совпадения;
- существенные пробелы;
- стоп-факторы;
- неподтверждённые предположения;
- причины оценки;
- рекомендацию по следующему действию.

Критерий готовности:

- результат имеет стабильную структурированную схему;
- некорректный или неполный ответ LLM обнаруживается и обрабатывается.

### MATCH-03. Реализовать воспроизводимый расчёт балла

Задачи:

- использовать LLM для извлечения фактов и классификации требований;
- рассчитывать итоговый балл по зафиксированным программным правилам;
- ограничивать максимальную оценку при критичных несоответствиях;
- уменьшать уверенность при отсутствии данных;
- сохранять версию алгоритма вместе с результатом.

Критерий готовности:

- одинаковые структурированные входные данные дают одинаковый итоговый балл;
- итоговую оценку можно объяснить через её составляющие.

### MATCH-04. Добавить категории вакансий

Базовые диапазоны:

- `85–100%` — «Точное попадание»;
- `70–84%` — «В зоне интереса»;
- `50–69%` — «На границе»;
- ниже `50%` — скрыто из основной выдачи по умолчанию.

Отдельное решение:

- определить «Амбициозный вариант» как самостоятельный признак перспективности либо заменить им категорию «На границе».

Критерий готовности:

- каждая оценённая вакансия получает однозначную категорию;
- границы категорий одинаковы во всех экранах и API.

### MATCH-05. Создать карточку объяснимого совпадения

На карточке показывать:

- процент и категорию;
- две или три главные причины совпадения;
- критичные пробелы;
- зарплату;
- формат работы;
- дату обнаружения;
- источник;
- действия «Открыть», «Сохранить» и «Проверить подробно».

Критерий готовности:

- пользователь понимает главные причины оценки без перехода в детальный анализ.

### MATCH-06. Добавить сортировку и фильтры

Задачи:

- сортировка по релевантности;
- сортировка по дате публикации;
- сортировка по зарплате;
- фильтр по категории;
- фильтр по источнику;
- фильтр по формату работы;
- переключатель показа вакансий ниже порога.

Критерий готовности:

- фильтры не изменяют сохранённую оценку;
- выбранные параметры явно отображаются и могут быть сброшены.

### MATCH-07. Собирать обратную связь пользователя

Задачи:

- действия «Оценка верна» и «Не подходит»;
- причины: роль, уровень, зарплата, компания, стек, локация или другое;
- хранить обратную связь отдельно от результата алгоритма;
- подготовить данные для последующей калибровки.

Критерий готовности:

- пользовательская оценка не переписывает исходный результат;
- можно анализировать расхождения между алгоритмом и пользователями.

### MATCH-08. Проверить качество оценки

Минимальные сценарии:

- полное совпадение;
- совпадение по навыкам при неверном уровне;
- отсутствие обязательного навыка;
- нежелательная компания;
- неизвестная зарплата;
- неполное описание вакансии;
- неоднозначно сформулированное требование;
- одна вакансия из разных источников.

Критерий готовности:

- все сценарии входят в повторяемый регрессионный набор;
- ожидаемое поведение для каждого сценария зафиксировано.

## FEED — персональная лента вакансий

`FEED` означает «лента». Направление объединяет результаты отдельных поисков в постоянное рабочее пространство пользователя.

### FEED-01. Добавить избранное

Задачи:

- сохранить вакансию;
- убрать вакансию из избранного;
- показывать сохранённые вакансии отдельно;
- сохранять состояние между поисками;
- не терять сохранённую вакансию после закрытия источника.

Критерий готовности:

- избранное принадлежит конкретному пользователю и не зависит от отдельного запуска поиска.

### FEED-02. Добавить пользовательские статусы

Начальный набор:

- новая;
- просмотрена;
- сохранена;
- планирую отклик;
- откликнулся;
- не подходит;
- закрыта.

Задачи:

- определить допустимые переходы между статусами;
- хранить дату изменения;
- разрешить возвращение к предыдущему статусу;
- не смешивать пользовательский статус и состояние вакансии на источнике.

Критерий готовности:

- статус сохраняется между поисками и однозначно отражает действие пользователя.

### FEED-03. Добавить причины исключения

Причины:

- компания;
- технология;
- зарплата;
- уровень;
- локация;
- формат работы;
- нерелевантная роль;
- другое.

Задачи:

- сохранять причину вместе с действием;
- разрешить отменить исключение;
- предлагать повторяющиеся причины как постоянное предпочтение профиля.

Критерий готовности:

- исключённая вакансия не появляется в основной ленте как новая;
- пользователь может найти и восстановить её.

### FEED-04. Объединить результаты разных поисков

Задачи:

- отображать одну вакансию один раз;
- сохранять дату первого и последнего обнаружения;
- показывать, в каких поисках она появлялась;
- не сбрасывать пользовательский статус при новом поиске;
- сохранять связь вакансии со всеми релевантными профилями и поисками.

Критерий готовности:

- повторное обнаружение не создаёт визуальный дубль и не удаляет пользовательские действия.

### FEED-05. Добавить состояния вакансии

Состояния:

- новая для пользователя;
- обновлённая;
- повторно найденная;
- закрытая источником;
- устаревшая;
- недоступная для проверки.

Критерий готовности:

- состояние источника отделено от статуса пользователя;
- интерфейс объясняет причину каждого специального состояния.

### FEED-06. Создать главную персональную ленту

Блоки ленты:

- новые точные совпадения;
- сохранённые вакансии;
- вакансии, требующие действия;
- недавно обновлённые позиции;
- переход в табличный режим;
- экспорт в CSV.

Критерий готовности:

- пользователь видит единое актуальное состояние вакансий без выбора конкретного запуска поиска.

### FEED-07. Добавить архив и скрытые вакансии

Задачи:

- исключить отклонённые вакансии из основной ленты;
- добавить просмотр архива;
- разрешить восстановление вакансии;
- не предлагать отклонённую вакансию повторно как новую.

Критерий готовности:

- скрытие обратимо;
- архив не влияет на исторические данные поисков.

## MARKET — карта рынка

`MARKET` означает «рынок». Направление агрегирует вакансии и показывает пользователю общую картину доступного ему рынка труда.

### MARKET-01. Нормализовать рыночные данные

Задачи:

- нормализовать валюту и период зарплаты;
- нормализовать город и регион;
- выделять удалённый, гибридный и офисный формат;
- нормализовать названия должностей;
- нормализовать грейды;
- объединять синонимы навыков;
- нормализовать компании и отрасли.

Критерий готовности:

- одинаковые сущности из разных источников агрегируются вместе;
- исходное значение сохраняется для проверки.

### MARKET-02. Определить аналитическую выборку

Задачи:

- решить, анализировать только подходящие вакансии или весь найденный рынок;
- определить минимальный порог совпадения;
- определить период анализа;
- определить правила учёта дублей;
- определить правила работы с вакансиями без зарплаты;
- показывать размер выборки.

Критерий готовности:

- каждый показатель имеет однозначно определённую выборку;
- пользователь понимает ограничения расчёта.

### MARKET-03. Рассчитывать базовые метрики

Метрики:

- количество активных вакансий;
- количество новых вакансий за период;
- медианная зарплата и диапазон;
- частые навыки;
- активно нанимающие компании;
- города и форматы работы;
- распределение по категориям совпадения.

Критерий готовности:

- показатели воспроизводимы на одной выборке;
- из показателя можно перейти к вакансиям, на которых он основан.

### MARKET-04. Сохранять исторические снимки

Задачи:

- создавать периодические снимки метрик;
- сохранять версию профиля и алгоритма;
- сравнивать неделю с неделей и месяц с месяцем;
- определить минимальный объём выборки для отображения тренда.

Критерий готовности:

- сравниваются только сопоставимые данные;
- недостаточный объём данных явно обозначается.

### MARKET-05. Создать экран карты рынка

Состав экрана:

- основные показатели;
- фильтры периода и направления;
- источник и размер выборки;
- предупреждение о неполных данных;
- переход от агрегата к исходным вакансиям.

Критерий готовности:

- пользователь может ответить, как выглядит доступный ему рынок и на каких данных основан вывод.

### MARKET-06. Выявлять значимые изменения

Сигналы:

- рост или падение спроса;
- изменение зарплат;
- новый часто встречающийся навык;
- новая активно нанимающая компания;
- изменение распределения форматов работы.

Задачи:

- определить практический порог значимости;
- не создавать сигнал при слишком маленькой выборке;
- объяснять период и данные сравнения.

Критерий готовности:

- каждый сигнал содержит величину изменения, период, выборку и ссылку на подтверждающие вакансии.

## SKILL — навыки и точки роста

`SKILL` означает «навык». Направление сравнивает профиль пользователя с требованиями множества релевантных вакансий и выявляет системные пробелы.

### SKILL-01. Создать единый справочник навыков

Задачи:

- определить канонические названия;
- хранить синонимы и варианты написания;
- разделить навыки по категориям;
- хранить связи между навыками;
- версионировать справочник.

Критерий готовности:

- варианты написания одного навыка не считаются разными навыками;
- исходная формулировка остаётся доступна.

### SKILL-02. Извлекать требования вакансии

Для каждого требования хранить:

- навык;
- обязательность;
- требуемый уровень;
- подтверждающий фрагмент описания;
- уверенность извлечения.

Критерий готовности:

- каждое извлечённое требование можно проверить по исходному описанию вакансии;
- неопределённые требования явно помечаются.

### SKILL-03. Строить матрицу пробелов

Состояния навыка:

- есть и подтверждён;
- заявлен, но недостаточно подтверждён;
- отсутствует;
- недостаточно данных.

Дополнительные признаки:

- обязательный или желательный;
- частота требования среди релевантных вакансий;
- уровень, ожидаемый рынком.

Критерий готовности:

- система отличает отсутствие навыка от отсутствия информации о нём.

### SKILL-04. Оценивать потенциальный эффект навыка

Показывать:

- в скольких релевантных вакансиях встречается навык;
- сколько дополнительных вакансий потенциально станет доступно;
- связь навыка с зарплатой;
- связь с конкретным карьерным направлением.

Критерий готовности:

- оценка основана на видимой выборке;
- результат сформулирован как потенциальный эффект, а не гарантия.

### SKILL-05. Приоритизировать навыки

Факторы:

- частота спроса;
- критичность;
- близость к текущему опыту;
- потенциальный прирост возможностей;
- ориентировочная сложность освоения;
- выбранная карьерная цель.

Критерий готовности:

- для каждого приоритета показаны факторы, повлиявшие на его позицию;
- пользователь может исключить нерелевантный навык.

### SKILL-06. Формировать персональный план развития

Состав плана:

- карьерная цель;
- приоритетные навыки;
- рекомендуемая последовательность;
- проверяемый результат каждого шага;
- связь шага с вакансиями или направлением;
- возможность отметить навык как уже имеющийся или нерелевантный.

Критерий готовности:

- каждый шаг связан с конкретной целью и ожидаемым эффектом;
- изменение данных профиля позволяет актуализировать план.

## INFRA — инфраструктура и безопасность

`INFRA` объединяет задачи, необходимые для безопасного production-развёртывания КарьеРадара.

### INFRA-01. Подготовить production-конфигурацию Nginx

Задачи:

- настроить reverse proxy для frontend;
- закрыть прямой внешний доступ к backend и PostgreSQL;
- предусмотреть передачу корректных proxy-заголовков;
- настроить ограничения размера запроса с учётом загрузки резюме;
- определить таймауты для длительного анализа и поиска;
- настроить HTTP-перенаправление на HTTPS;
- подготовить подключение TLS-сертификата;
- добавить безопасные HTTP-заголовки;
- проверить конфигурацию штатной командой Nginx.

Критерий готовности:

- снаружи доступен только публичный HTTPS-вход;
- frontend работает через Nginx;
- backend и PostgreSQL недоступны напрямую из интернета;
- загрузка резюме и длительные операции не обрываются из-за настроек proxy;
- конфигурация проходит проверку Nginx.

### INFRA-02. Проверить frontend на уязвимости

Задачи:

- проверить зависимости на известные уязвимости;
- проверить хранение JWT и завершение пользовательской сессии;
- проверить все места отображения данных резюме, вакансий и LLM-ответов на XSS;
- проверить обработку внешних ссылок;
- проверить загрузку файлов, допустимые типы и ограничения размера;
- проверить отсутствие секретов и персональных данных в клиентском коде и сообщениях об ошибках;
- подтвердить, что frontend не имеет прямого production-доступа к PostgreSQL;
- зафиксировать найденные проблемы, уровень риска и решение по каждой из них.

Критерий готовности:

- критические и высокие уязвимости исправлены до выпуска;
- для средних и низких рисков зафиксировано решение или отдельная задача;
- результат проверки можно повторить перед следующим релизом.

### INFRA-03. Подготовить VPS и купить доменное имя

Задачи:

- выбрать и приобрести доменное имя;
- выбрать VPS с достаточными ресурсами для backend, Playwright, frontend и PostgreSQL;
- настроить DNS-записи домена;
- создать отдельного пользователя для развёртывания;
- настроить SSH-доступ по ключам и отключить небезопасные способы входа;
- настроить firewall и открыть только необходимые порты;
- установить и настроить Docker с Compose;
- подготовить каталоги, volumes, переменные окружения и секреты;
- настроить TLS-сертификат и его автоматическое обновление;
- определить резервное копирование PostgreSQL и процедуру восстановления;
- выполнить тестовое развёртывание и перезапуск сервисов.

Критерий готовности:

- домен указывает на VPS;
- приложение открывается по HTTPS;
- наружу опубликованы только необходимые порты;
- секреты не хранятся в репозитории;
- данные переживают перезапуск контейнеров;
- процедура резервного копирования и восстановления проверена.

## Взаимосвязь направлений

```text
CORE: профиль и предпочтения пользователя
                 |
                 v
MATCH: оценка отдельных вакансий
                 |
          +------+------+
          |             |
          v             v
FEED: работа       MARKET: общая
с вакансиями       картина рынка
          |             |
          +------+------+
                 |
                 v
SKILL: пробелы и план развития

INFRA: безопасное production-развёртывание всех компонентов
```

`CORE` формирует основу данных. `MATCH` оценивает отдельные вакансии. `FEED` организует ежедневную работу с ними. `MARKET` показывает агрегированную картину. `SKILL` превращает рыночные данные в рекомендации по развитию.

`INFRA` обеспечивает безопасную публикацию и эксплуатацию продукта и поддерживает все остальные направления.

## Рекомендуемый первый рабочий срез

1. `INFRA-01` — production-конфигурация Nginx.
2. `INFRA-02` — проверка frontend на уязвимости.
3. `INFRA-03` — VPS, домен, HTTPS и базовая эксплуатационная подготовка.
4. `CORE-01` — схема и происхождение данных профиля.
5. `CORE-03` — модель пользовательских предпочтений.
6. `MATCH-01` — правила оценки.
7. `MATCH-02` — структурированный результат анализа.
8. `MATCH-03` — воспроизводимый итоговый балл.
9. `MATCH-04` — категории выдачи.
10. `MATCH-08` — эталонный набор проверочных сценариев.

Результатом этого среза должна стать подготовленная основа версии `0.5.0`: от безопасного production-развёртывания и модели данных до проверяемой объяснимой оценки вакансии.
