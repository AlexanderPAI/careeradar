# КарьеРадар

Персональная система карьерной навигации, которая превращает резюме в структурированный профиль, находит подходящие вакансии и помогает оценить готовность к отклику.

Версия: `0.4.1`

## Что делает проект

КарьеРадар принимает резюме, извлекает из него профиль кандидата и формирует персональный поисковый запрос. Система собирает вакансии с hh.ru и Хабр Карьеры, удаляет дубли и с помощью LLM отбирает возможности, соответствующие опыту, навыкам и ожиданиям кандидата.

Помимо подбора, КарьеРадар формирует практические рекомендации по улучшению резюме и подробно сопоставляет профиль с отдельной вакансией: показывает подтверждённые совпадения, пробелы и риски, вопросы для уточнения и рекомендацию по отклику.

Профили, история подборов, найденные вакансии, рекомендации и результаты анализа сохраняются в PostgreSQL и изолированы между пользователями. Пользователь может возвращаться к сохранённым профилям, обновлять подбор, проверять соответствие вакансии и экспортировать выдачу в CSV. Для LLM-агентов поддерживаются GigaChat и OpenRouter.

Версия `0.4.1` унифицирует работу с вакансиями: новый подбор и сохранённый профиль используют одно интерактивное представление с переходом к вакансии и запуском проверки соответствия.

## Возможности

- Загрузка резюме через веб-интерфейс Streamlit.
- Вход по логину и паролю с JWT-авторизацией.
- Изоляция профилей и подборов между пользователями.
- Выбор LLM-провайдера: GigaChat или OpenRouter.
- Извлечение текста из файлов `.pdf`, `.docx` и `.txt`.
- Автоматическое извлечение профиля кандидата из резюме.
- Практические LLM-рекомендации по улучшению резюме.
- Генерация поискового запроса для вакансий.
- Поиск вакансий на hh.ru.
- Поиск вакансий на Хабр Карьере.
- Объединение результатов hh.ru и Хабр Карьеры в единую выдачу.
- Удаление дублей по ссылкам.
- LLM-фильтрация вакансий по профилю кандидата.
- Сохранение профилей и истории подборов в PostgreSQL.
- Просмотр списка сохранённых профилей.
- Отдельная страница полного профиля с последним результатом поиска.
- Отображение даты и времени последнего подбора.
- Повторный подбор вакансий для сохранённого профиля.
- Загрузка полного описания отдельной вакансии с hh.ru или Хабр Карьеры.
- Сопоставление резюме с конкретной вакансией: совпадения, пробелы, вопросы и рекомендация по отклику.
- Сохранение и просмотр истории анализов вакансий.
- Просмотр вакансий в интерактивном списке с действиями внутри UI.
- Экспорт итоговой выдачи в CSV без промежуточного хранения CSV на backend.

## Граница текущей версии

В `v0.4.1` уже есть качественный анализ отдельной вакансии. Он показывает одно из заключений — высокое, частичное или низкое соответствие — и формирует разделы с подтверждёнными совпадениями, пробелами, рисками, вопросами и рекомендацией по отклику.

Этот анализ запускается пользователем отдельно для выбранной вакансии и сохраняется как Markdown-текст. Он пока не является числовым matching-механизмом: воспроизводимого процента, структурированных факторов оценки и объяснений непосредственно в общем списке вакансий нет.

В базе уже существуют отдельные записи вакансий, связи вакансий с разными поисками и даты первого и последнего обнаружения. Однако интерфейс показывает результаты конкретного последнего поиска, а не единую персональную ленту. Избранное, пользовательские статусы и определение изменившихся или закрытых вакансий ещё не реализованы.

Актуальный статус этапов развития приведён в [продуктовом roadmap](docs/ROADMAP.md), а задачи и план релизов — в [общем backlog](docs/BACKLOG.md).

## Основной пользовательский сценарий

1. Пользователь входит в веб-интерфейс по логину и паролю.
2. Загружает резюме.
3. Нажимает `Анализировать резюме`.
4. Система показывает профиль, краткое описание и поисковый запрос.
5. Пользователь нажимает `Сканировать рынок`.
6. Backend собирает вакансии с hh.ru и Хабр Карьеры.
7. Агент фильтрует вакансии по профилю кандидата.
8. Пользователь просматривает список вакансий, при необходимости открывает источник или запускает проверку соответствия и скачивает CSV.
9. В профиле можно получить и сохранить рекомендации по улучшению резюме.
10. Для отдельной вакансии можно запустить подробное сопоставление с резюме.
11. Заключение показывает совпадения, пробелы и риски, вопросы для уточнения и рекомендацию по отклику.
12. Профиль, результаты и история анализов остаются доступны только владельцу.
13. С детальной страницы профиля можно повторить подбор вакансий.

## Переменные окружения

Для работы приложения нужно выбрать LLM-провайдера, указать его ключ, параметры PostgreSQL и JWT-секрет.

Создайте файл `.env` в корне проекта:

```env
OPENROUTER_KEY=your_openrouter_api_key
GIGACHAT_KEY=your_gigachat_authorization_key
GIGACHAT_MODEL=GigaChat
GIGACHAT_URL=https://api.giga.chat/v1/chat/completions
GIGACHAT_VERIFY_SSL_CERTS=false
LLM_PROVIDER=gigachat
POSTGRES_USER=careeradar
POSTGRES_PASSWORD=<случайное значение длиной не менее 20 символов>
POSTGRES_HOST=db
POSTGRES_PORT=5432
POSTGRES_DB=careeradar
JWT_SECRET=<отдельное случайное значение длиной не менее 48 символов>
JWT_EXPIRE_MINUTES=480
```

`LLM_PROVIDER` принимает `gigachat` или `openrouter`. Значения `OPENROUTER_KEY`, `GIGACHAT_KEY` и `JWT_SECRET` указывайте без кавычек: некоторые способы передачи `.env` в Docker сохраняют кавычки как часть секрета.

Для production сгенерируйте разные значения, например двумя отдельными
вызовами `openssl rand -base64 48`. Backend до запуска отклоняет известные
шаблоны (`change_me`, `replace_with...`, демонстрационные секреты), короткие и
слишком однообразные значения.

### Доступность провайдеров и источников

OpenRouter не работает при обращении с IP-адресов РФ, а парсинг hh.ru не работает при обращении с иностранных IP-адресов. Поэтому для запуска КарьеРадара в РФ рекомендуется выбрать GigaChat: задайте `LLM_PROVIDER=gigachat` и укажите действующий `GIGACHAT_KEY`.

## Запуск через Docker Compose

```bash
docker compose up --build
```

После запуска:

- Frontend: `http://localhost:8501`

Backend и PostgreSQL не публикуют порты на хост. Backend доступен только frontend-контейнеру во внутренней Docker-сети.

## Пользователи и вход

Публичной регистрации нет. После запуска создайте пользователя из backend-контейнера:

```bash
docker compose exec backend python -m backend.create_user username
```

Скрипт интерактивно запросит пароль (минимум 8 символов). После этого пользователь может войти на `http://localhost:8501`. Все страницы интерфейса, API профилей, поисков и фильтрации требуют JWT, а история фильтруется по владельцу.

## Миграции

При запуске через Docker Compose backend автоматически выполняет `alembic upgrade head` после готовности PostgreSQL.

Для ручной работы с миграциями:

```bash
alembic -c backend/alembic.ini revision --autogenerate -m "migration_name"
alembic -c backend/alembic.ini upgrade head
```

## API

Все маршруты профилей, поиска и фильтрации требуют `Authorization: Bearer <token>`.

### Вход

```http
POST /v1/auth/token
```

Принимает `username` и `password` как OAuth2 form data и возвращает JWT access token.

Неуспешные попытки входа записываются в аудит и ограничиваются за скользящее
15-минутное окно: не более 5 попыток на логин и 20 попыток на IP-адрес.
Повторные ошибки получают нарастающую задержку, а превышение лимита — ответ
`429 Too Many Requests` с заголовком `Retry-After`. Пороговые значения и задержки
настраиваются переменными `AUTH_RATE_LIMIT_*` и `AUTH_FAILURE_DELAY_*`.

### Анализ резюме

```http
POST /v1/cv_analyzer/send_cv
```

Принимает файл резюме и возвращает:

- `search_prompt` - поисковый запрос для агента подбора вакансий;
- `user_profile` - структурированный профиль кандидата.
- `profile_id` - UUID сохранённого профиля.

### Поиск вакансий

```http
POST /v1/searcher/chat
```

Принимает:

- `message` - текст поискового запроса;
- `profile_id` - UUID профиля кандидата.

Возвращает `search_id` — UUID сохранённого запуска поиска. Вакансии сохраняются в PostgreSQL.

### Фильтрация вакансий

```http
POST /v1/filter/check
```

Принимает `search_id`, загружает профиль и найденные вакансии из PostgreSQL, сохраняет результат LLM-фильтрации и возвращает JSON со списком подходящих вакансий.

### Рекомендации по резюме

```http
POST /v1/resume_advisor/recommendations
```

Принимает `profile_id`, анализирует сохранённые профиль и текст резюме, сохраняет рекомендации и возвращает их вместе с `recommendation_id`.

### Анализ соответствия вакансии

```http
POST /v1/vacancy_match/analyze
```

Принимает `profile_id` и `vacancy_id`. Backend проверяет принадлежность профиля и вакансии пользователю, загружает актуальное полное описание вакансии с hh.ru или Хабр Карьеры, сопоставляет его с резюме и сохраняет заключение. В ответ возвращается `analysis_id`.

### История анализов вакансий

```http
GET /v1/history/vacancy-analyses
GET /v1/history/vacancy-analyses/{analysis_id}
```

Возвращает список сохранённых анализов текущего пользователя или детальный результат выбранного сопоставления.

## Хранение данных

В PostgreSQL используются семь основных сущностей:

- `users` — учётные записи, хеши паролей и статус активности;
- `candidate_profiles` — структурированные профили кандидатов, исходный JSON и текст резюме;
- `search_runs` — история запусков поиска, запросы, фильтры и статистика;
- `vacancies` — дедуплицированные вакансии из разных источников;
- `search_results` — связь поиска с вакансией, порядок выдачи и результат фильтрации;
- `resume_recommendations` — сохранённые рекомендации по резюме для профиля;
- `vacancy_analyses` — результаты сопоставления профиля с вакансией и снимок её данных на момент проверки.

Frontend получает профили и историю только через защищённый backend API. Прямого сетевого доступа frontend к PostgreSQL нет.

## Ограничения

- Подбор зависит от качества распознавания резюме и ответа LLM.
- Публичной регистрации нет: учётные записи создаются администратором через CLI.
- Фильтрация вакансий выполняется батчами и может занимать время.
- Парсинг внешних сайтов зависит от доступности hh.ru и Хабр Карьеры.
- Анализ отдельной вакансии недоступен, если её страница закрыта, заблокировала загрузку или больше не существует.
- Профиль пока нельзя редактировать вручную из UI.
- Загруженные файлы резюме сохраняются локально в `backend/storage/cv` с
  правами `0600`, каталог имеет права `0700`. Исходный файл и извлечённый текст
  автоматически удаляются через 30 дней (срок задаётся
  `RESUME_RETENTION_DAYS`). Пользователь также может удалить профиль вместе со
  всеми связанными данными в интерфейсе.
- Тип резюме определяется backend по содержимому, а не по переданному браузером
  `Content-Type`. Проверяются сигнатура PDF/DOC, внутренняя структура DOCX или
  корректный UTF-8 для TXT и соответствие расширению имени. Максимальный размер
  и ограничения DOCX задаются переменными `RESUME_UPLOAD_*` и `RESUME_DOCX_*`.
- Backend самостоятельно ограничивает тело любого HTTP-запроса 25 МБ, включая
  запросы без `Content-Length`. Байты считаются во входящем потоке, а запись
  загружаемого резюме имеет дополнительный потоковый лимит. Общий предел
  настраивается через `REQUEST_BODY_MAX_BYTES`.
- Каждый документ до обработки потоково проверяется отдельным сервисом ClamAV.
  При обнаружении вредоносного содержимого или недоступности сканера backend
  удаляет файл и не запускает парсер. Извлечение текста выполняется в одноразовом
  дочернем процессе с лимитами CPU, памяти, времени, файловых дескрипторов и
  размера результата. Настройки задаются через `MALWARE_SCAN_*` и
  `DOCUMENT_PARSER_*`; отключение сканирования запрещено в production.
- Перед обращением к внешней LLM требуется явное согласие пользователя. Состав,
  цели и правила минимизации передаваемых данных описаны в
  [политике обработки данных LLM](docs/LLM_DATA_PROCESSING.md).
- Проверка TLS GigaChat включена по умолчанию; цепочка НУЦ Минцифры и порядок
  её обновления описаны в [руководстве по TLS](docs/GIGACHAT_TLS.md).
- Старый бинарный формат `.doc` присутствует в списке разрешённых загрузок, но обрабатывается DOCX-ридером и не имеет подтверждённой надёжной поддержки. Для работы следует использовать `.docx`, `.pdf` или `.txt`.
- В проекте пока нет автоматических модульных, интеграционных и сквозных тестов.
